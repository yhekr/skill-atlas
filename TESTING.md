# Проверка Skill Atlas 1.0.1

## Память проекта

30 сентября 2026 добавлены [память](memory/README.md), [скилл её поддержки](.agents/skills/maintain-project-memory/SKILL.md) и правила чтения/обновления в AGENTS. Скилл прошёл `quick_validate.py` из skill-creator. Проверены относительные ссылки и отсутствие повреждённых UTF-8-символов в файлах памяти, скилле и AGENTS. Реальный запуск CLI `scan .agents --json` нашёл ровно один `maintain-project-memory` с корректными метаданными и без предупреждений. Форматирование, Release-сборка и 161 тест .NET прошли. UI не изменялся; новую сессию Codex для проверки автоматического подключения не запускали.

## Звёздочки

1 октября 2026 добавлены звёздочки в веб-интерфейсе ([skill-stars.mjs](src/SkillAtlas.Web/wwwroot/skill-stars.mjs)). `node --test tests/web/skill-filter.test.mjs tests/web/skill-stars.test.mjs` локально прошёл: **39 тестов JavaScript** (21 фильтра и 18 звёздочек). Они покрывают пустое хранилище, включение и выключение, сохранение между загрузками, регистр репозитория и пути, тот же путь в другом репозитории, повреждённые и неверные данные, `__proto__` и HTML в путях, слияние изменений двух вкладок, недоступное или переполненное `localStorage` и восстановление после ошибки записи. Веб-тест проверяет HTTP-тип нового модуля и наличие элементов управления на странице.

В этой среде не было .NET SDK, PowerShell и браузера, а сеть для их загрузки была закрыта. Поэтому `dotnet format`, сборка, тесты .NET, pack/publish и проверка в настоящем браузере **не выполнялись**. Связка `app.js` проверена только во временном Node-скрипте с имитацией DOM (не коммитится): звёздочка в списке и над документом, фокус после перерисовки, режим Starred, сочетание с фильтром, событие `storage` из другой вкладки, предупреждение при ошибке записи и сброс режима при новом сканировании. Это не заменяет проверку интерфейса в браузере.

## Запуск Codex в sandbox

`scripts/test-sbx-codex.sh` проверяет `sbx-codex.sh` с настоящими Git worktree и jq; Central и sbx подменяются тестовыми исполняемыми файлами. 36 общих сценариев и один дополнительный на Windows включают создание и повторное использование worktree, сохранение незакоммиченных файлов, существующие/занятые ветки, чужие репозитории, detached HEAD, отсутствие sbx, пробелы и shell-символы в аргументах, неверные имена, порты, JSON и ключи, CRLF, ошибки Central и коды выхода sbx. Проверяются границы имени (2 и 63), монтирование общего `.git`, запуск из другого/перемещённого worktree, разделение `create` и `run`, повторное подключение с новым ключом, отказ от чужого sandbox, ошибки инвентаризации и политики, отказ при явном запрете, разрешение только нужного порта в пределах sandbox и отсутствие повторного правила. Windows-сценарий проверяет регистр и разделители в путях из `sbx ls --json`. Сети и модельных запросов в этих тестах нет.

Ручной прогон `SBX_TEST_DOCKER=1 bash scripts/test-sbx-codex.sh` добавляет ещё один сценарий: настоящий Linux-контейнер Alpine/Git получает только временный worktree и общий `.git` с путями из вызова скрипта. Проверяются чистый `git status`, создание коммита, видимость коммита на хосте и неизменность исходной ветки. На Windows тест отдельно проверяет передачу `GIT_DIR`/`GIT_WORK_TREE` через нативный процесс и воспроизводит ошибку Windows-указателя `.git` без этих переменных. Настоящие ключи не используются. Этот дополнительный тест требует Docker и сети для загрузки образа/пакета; в обычный прогон CI не включён.

Central 1.11.0: `proxy start --return-key` возвращает ключ; обработчик Responses на порту 19516 возвращает ожидаемый HTTP 400 `model must be set` на пустой авторизованный запрос. Это проверено и с хоста, и из настоящего sbx. GET `/models` возвращает 404 и не используется как проверка готовности. Ключи не печатались.

Повторная проверка 30 сентября 2026 на Windows, Docker Desktop 4.93.0 / Engine 29.8.1 и sbx 0.46.0:

- `docker run --rm hello-world` завершился успешно. Запрос из `curlimages/curl` к Central через `host.docker.internal:19516` с заведомо неверным тестовым ключом получил HTTP 403 `invalid proxy secret`: сетевой путь из обычного контейнера работает. Это не проверка авторизованного модельного запроса.
- После уточнения исходного примера исправлено монтирование Git: `.git` — отдельная папка, а не специальный аргумент `:git`. Worktree и общий каталог Git передаются как две рабочие папки. Работа Git с таким набором монтирований проверена в настоящем Docker-контейнере.
- **Полный запуск подтверждён.** Исходный образ `docker/sandbox-templates:codex-docker` подготовлен; `sbx-codex.sh … -- --version` в TTY создал sandbox и вывел `codex-cli 0.149.1`. Повторный запуск того же sandbox с `exec --ephemeral` получил `CENTRAL_OK` через провайдер `jetbrains_central`, модель по умолчанию `gpt-5.6-sol`.
- Отдельный новый sandbox во временном Git-репозитории создан исправленным скриптом: правило `localhost:19516` добавилось автоматически, `--version` прошёл, повторное подключение получило от модели `CENTRAL_FRESH_OK`. Внутри настоящего sbx выполнены `git status` и коммит; коммит виден с хоста в тестовом worktree, исходная ветка сохранила начальный коммит. Временный sandbox после проверки удалён.
- Диагностика Windows выявила независимые проблемы среды: сначала мешали длинный TEMP/оставшиеся сокеты, затем распаковка остановилась с `No space left on device`. После освобождения места плавающий `Access is denied` воспроизведён без Docker: 5 отказов из 200 переименований; Procmon показал открытые SpaceSniffer подпапки в момент отказа. После закрытия SpaceSniffer все 500 переименований прошли, затем прошла подготовка настоящего образа. Права администратора до закрытия сканера не помогали. Защита Windows и ACL не ослаблялись, полного сброса Sandboxes не было.

После исправлений прошли 37 сценариев launcher на Windows и все 38 при `SBX_TEST_DOCKER=1`. `dotnet format --verify-no-changes --no-restore`, `dotnet build -c Release` и `dotnet test -c Release --no-build` прошли: 161 тест (135 Core/CLI + 26 Web), сборка без предупреждений и ошибок.
